v0.2.0 introduces admin-side user deletion (backend endpoint + frontend danger zone) and resolves four cross-component runtime bugs surfaced during real-world use — LAN HTTP environments crashing notifications/tabs/uploads, non-closable Files/Music/Video tabs, an unresponsive ForbiddenPanel action button, and a stale About-dialog version literal. The release script now keeps all three version sources (VERSION, `package.json`, `frontend/package.json`) in lockstep.

---

## 1. Features

### 1.1 Admin user delete

Admins can remove users entirely from the UserManager detail panel. The operation hard-deletes the user record together with associated intents, identities, and log rows inside a single transaction.

**Backend** (commit `e4d2b0b`):
- `DELETE /server/users/{userId}` registered inside the admin-gated token group (`backend/internal/server/router.go`).
- `admin.Handlers.DeleteUser` enforces the ADMIN role, refuses self-delete with HTTP 400 to prevent admin lockout, and maps `db.ErrUserNotFound` to HTTP 404.
- `db.DeleteUser` runs the cascade inside a transaction: explicitly removes log rows first (because the existing `log.user_id NOT NULL` schema combined with `ON DELETE SET NULL` would otherwise violate the NOT NULL constraint — a latent schema bug now worked around at the application layer), then deletes the user. `user_intents` and `user_identities` cascade via foreign key as designed.
- `db.ErrUserNotFound` sentinel introduced for clean 404 mapping.
- Test fixture `fullSchema` updated to add the missing `FOREIGN KEY ... ON DELETE CASCADE` on `user_identities` so test coverage matches production behavior.

**Frontend** (commit `281a466`):
- `UserManager.svelte` detail panel gains a danger zone below the intents card with a Trash2 icon and a "Delete user" button.
- Confirmation dialog: `Delete user "<label>" (<id>)? This cannot be undone.`
- On accept the panel issues `DELETE /server/users/{userId}` and refreshes the user list on success.
- The button is disabled with an inline explanation when an admin views their own row (the same guard the backend enforces; the UI surface prevents the request from being attempted at all).
- Success and error are surfaced through the existing notifications store.

## 2. Fixes

### 2.1 LAN HTTP access crashed notifications, tabs, and uploads

(commit `025fe58`)

**Symptom:** On installations accessed via raw LAN HTTP (`http://192.168.x.x`) rather than HTTPS or localhost, opening a tab, enqueuing an upload, or triggering any notification immediately threw an uncaught error. The auth flow that called the notifier on login failure then aborted as well, leaving the user with a frozen UI.

**Root cause:** Three stores (`notifications.svelte.ts`, `tabs.svelte.ts`, `uploads.svelte.ts`) generated UI keys with a one-liner that called `crypto.randomUUID()` directly. `crypto.randomUUID` is only exposed in secure contexts — over plain HTTP outside `localhost`, `crypto` is defined but the `randomUUID` member is not, so the call threw on every invocation.

**Fix:** Extracted a shared helper at `frontend/src/lib/util/random-id.ts` that gates on `typeof crypto !== "undefined" && typeof crypto.randomUUID === "function"` and falls back to an RFC 4122 v4 implementation built on `Math.random`. The three stores now import this helper instead of inlining the call. These identifiers are UI keys (notification ids, tab ids, upload ids), not security tokens, so a non-cryptographic fallback is appropriate.

### 2.2 Files / Music / Video tabs had no close button

(commit `3008b73`)

**Symptom:** The default Files tab and the Music / Video singletons rendered without the standard close (X) control, so users could not dismiss them once opened.

**Root cause:** `TabStore.rootTab` was constructed with `closable: false`, and the sidebar's `activate` path explicitly forced the same flag for the Explorer / Music / Video singletons. The original intent — "the sidebar is the only way back in" — turned out to be moot because the sidebar already auto-focuses an existing tab and recreates a missing one, so the close button is non-destructive.

**Fix:** `rootTab` now opens with the store's default `closable: true`, and the sidebar's activation path no longer overrides it. `TabStore.close` was extended to handle the new edge case of closing the very last tab — it inserts a fresh Files `rootTab` and selects it so `TabContent` never renders an empty pane.

### 2.3 ForbiddenPanel "Request admin permission" button was unresponsive

(commit `6586f32`)

**Symptom:** New users hitting the `ForbiddenPanel` ("Files are locked") could click the "Request admin permission" button repeatedly without the prompt dialog ever appearing.

**Root cause:** `Explorer.svelte` wraps its content in a `<div data-marquee-canvas="true">` with an `onpointerdown` that calls `setPointerCapture`. `ForbiddenPanel` rendered inside this canvas without the opt-out marker that `FileGrid` and `FileList` already use, so `pointerup` was redirected to the canvas div and the click event never synthesized on the button. `prompt()` therefore never fired.

**Fix:** Added `data-marquee-canvas="false"` to the `ForbiddenPanel` root `<div>`, mirroring the opt-out pattern already in use elsewhere. The button now reliably triggers the prompt dialog.

### 2.4 About dialog showed stale "2.0.0"

(commit `63f3a22`)

The About dialog rendered a hardcoded `"2.0.0"` constant in its App version row while the StatusBar correctly displayed the build-time `__APP_VERSION__` constant. Removed the local literal; the dialog now reads `__APP_VERSION__` directly, so both UI surfaces show the same value (this release: `0.2.0`).

## 3. Infrastructure and Refactors

- **Release pipeline lockstep extended to root `package.json`** (commit `0d519ff`). `scripts/release.sh` previously synced only `VERSION` and `frontend/package.json` — the root `package.json` had been frozen at `"1.0.0"` since the Node-era backend was removed. The script now bumps both `package.json` files (via an extracted `sync_pkg_version()` helper) and stages both in the release commit. From v0.2.0 onward all three version sources match.
- **`.gitignore`** (commit `384ca76`). Added `/data/` and `/repo-visuals-work/` to prevent local data directories and scratch capture work from being accidentally tracked.

## 4. Verification Summary

**Backend** — Integration tests added alongside the new endpoint:
- `TestDeleteUser_CascadesIntentsAndIdentities` exercises the transaction path, asserting that the user, their intents, their identities, and their log rows are all removed.
- `TestDeleteUser_ReturnsErrUserNotFoundWhenMissing` verifies the sentinel maps cleanly to 404 in the handler layer.

Existing static checks, builds, and the broader integration suite remain unchanged.

**Frontend** — End-to-end browser scenarios covered every changed surface:
- Admin DELETE flow: an admin viewing their own row sees the disabled button (self-guard); deleting another user removes them from the list and resets the detail panel.
- `random-id` fallback: both the secure-context and forced-fallback paths produce UUID-v4-shaped strings; the notifications queue advances correctly in both modes.
- Tab closability: Files / Music / Video tabs now render the close control; closing them works; closing the very last open tab inserts a fresh Files tab.
- `ForbiddenPanel`: the "Request admin permission" button reliably triggers the prompt dialog.

## 5. Known Limitations and Follow-ups

- The root `package.json` still pins the frontend toolchain (Vite, SvelteKit, Tailwind, Svelte 5, TypeScript) used by the Docker build's first `npm ci`. Removing it cleanly requires migrating those devDependencies into `frontend/package.json` so the build can run entirely out of `frontend/`. Until that architecture cleanup lands, the release script keeps the root `version` field in lockstep so it does not drift again.
- The `log.user_id NOT NULL` + `ON DELETE SET NULL` schema mismatch is currently worked around in `db.DeleteUser` by deleting log rows explicitly. A schema migration to either drop the NOT NULL constraint or change the FK action would let the database enforce the cascade directly; tracked as a follow-up.
- Admin user delete is a hard delete with no undo. A soft-delete / restore flow is out of scope for v0.2.0 and would be a separate feature design.
