v0.3.1은 **production 대용량 파일 업로드 hotfix**다. v0.3.0의 tus 클라이언트는 모든 청크 PATCH에 transient 네트워크 실패에 대한 retry가 0이었다 — 멀티-GB 전송 중 Wi-Fi blip, 짧은 proxy 헐떡임, 또는 컨테이너 재시작 한 번이면 `ERR_CONNECTION_RESET`이 발생하고 전체 업로드가 abort되었다. store의 "Resume" 액션도 진짜 resume이 아니었다: `uploadedBytes`를 `0`으로 리셋하고 fresh-upload 경로를 호출 — 50 GB 업로드 재시도는 offset 0부터 다시 시작. 진짜 tus resume 함수는 클라이언트에 존재했지만 worker에 와이어링되지 않았다.

## 1. Fix — TUS 청크 재시도 + 진짜 resume

(commit `3c19a35`)

### v0.3.0의 결함

`frontend/src/lib/tus-client.ts`:
- `uploadChunk()`에 재시도 없음. `fetch` reject (transient 네트워크) 또는 `5xx` 응답 (서버 헐떡임)이 즉시 throw → 사용자에게 `ERR_CONNECTION_RESET` 노출.
- `resumeUpload(uploadUrl, ...)` (진짜 HEAD-then-PATCH-from-offset 구현)는 존재했으나 호출자 없음.

`frontend/src/lib/upload-worker.ts`:
- `runUpload()` catch → 즉시 `setStatus("error")`. transient/permanent 구분 없음.
- `resumeUpload(id)` (worker의 "Resume" 핸들러)는 `uploads.update(id, { status: "queued", uploadedBytes: 0 })` 수행. `uploadedBytes: 0` 리셋 + 저장된 tus URL 부재 = 다음 pump 사이클이 처음부터 fresh upload 생성.

가정용 회선에서 50 GB 전송 중: Wi-Fi blip 1회 → 전체 업로드 0부터 재시작. 사용자가 보는 실패 모드는 DevTools 콘솔의 `ERR_CONNECTION_RESET` + 업로드 패널의 `error` 표시.

### v0.3.1의 변경

**`tus-client.ts` — 재시도 + abort-aware backoff:**

- 신규 `RETRY_DELAYS_MS = [500, 1000, 2000, 4000, 8000]` (누적 ~15.5초 재시도 윈도).
- 신규 `isTransient(error)` predicate: `TypeError` (fetch 네트워크 reject)와 `TusError`의 `status === 0` 또는 `status >= 500`은 transient; `4xx`와 `AbortError`는 즉시 propagate.
- 신규 `delay(ms, signal)`: `ms` 후 resolve, 업로드의 `AbortSignal` 발화 시 즉시 reject. 재시도 backoff 중에 일시정지/취소가 즉시 반응.
- 신규 `withRetry<T>(operation, signal)`: `operation`을 `for` 루프로 감싸 transient 에러를 catch하고 다음 delay만큼 sleep 후 재시도. `RETRY_DELAYS_MS.length` 회 모두 실패하면 원본 에러 propagate.
- `uploadChunk()` body를 `withRetry`로 감쌈 — 청크가 이제 blip, 짧은 proxy timeout, 짧은 컨테이너 재시작 (watchtower rolling restart 보통 <10초)을 견딘다.
- `getOffset()`가 이제 `AbortSignal`을 받음 (worker에서 propagate) + 마찬가지로 `withRetry`로 감쌈 — resume 중 HEAD 복구도 동등하게 보호.
- `uploadFile()`이 신규 `onCreate(uploadUrl)` 콜백 노출. worker가 CREATE 응답 직후 tus Location URL을 저장하는 데 사용 — 진짜 resume에 필수.

**`upload-worker.ts` — tusUrl 저장 + 진짜 resume + transient→paused:**

- `buildTusOptions(upload)` 추출. `onCreate`를 `uploads.update(upload.id, { tusUrl: uploadUrl })`에 와이어링.
- `runUpload()` 이제 분기: `upload.tusUrl && upload.uploadedBytes > 0`이면 `resumeTusUpload(upload.tusUrl, ...)` (진짜 `tus-client.resumeUpload` — HEAD로 offset 조회 + 거기부터 PATCH) 호출. 그렇지 않으면 fresh `uploadFile(...)`.
- `handleUploadFailure(upload, error)` 추출. 실패를 3개 카테고리로 라우팅:
  - `AbortError` → silent (사용자가 cancel/pause)
  - `isTransient(error)` → `setStatus("paused", { errorMessage })`. `tusUrl`과 `uploadedBytes`는 upload row에 보존, 사용자가 "Resume"하면 마지막 서버 확인 offset부터 계속.
  - 그 외 (4xx auth/validation 등) → `setStatus("error")` — 영구 실패는 기존과 동일.
- `resumeUpload(id)` (worker public Resume 핸들러)가 `tusUrl` 존재 시 `uploadedBytes` 보존. reset-to-0은 `tusUrl`이 한 번도 저장된 적 없는 legacy state에 대한 fallback으로만 남음.

### 사용자가 보는 동작 변화

| 시나리오 | v0.3.0 | v0.3.1 |
|---|---|---|
| 단일 청크 PATCH transient 실패 (Wi-Fi blip, 짧은 502) | 전체 업로드 → `error`, 콘솔에 `ERR_CONNECTION_RESET` | 500ms, 1s, 2s, 4s, 8s 재시도. 그 15.5초 안에 성공하면 업로드 끊김 없이 진행. |
| 재시도 소진 후에도 실패 (지속적 outage) | 업로드 → `error`, 0부터 재시작 필수 | 업로드 → `paused`로 `tusUrl` + `uploadedBytes` 보존. "Resume" 클릭 시 마지막 서버 확인 offset부터 계속 (진짜 tus HEAD→PATCH). |
| 업로드 중 서버 재시작 (watchtower rolling restart, 보통 <10초) | `ERR_CONNECTION_RESET`, 업로드 손실 | 재시도가 재시작 윈도를 흡수. 업로드 계속. |
| 부분 업로드에서 Pause 후 Resume 클릭 | Resume이 0부터 재시작 | Resume이 마지막 확인 offset부터 계속. |
| 영구 4xx (auth 만료, forbidden, 잘못된 메타데이터) | `error` 상태 | `error` 상태 (변경 없음 — retry해도 의미 없음). |

### 변경되지 않은 것

- 서버 측: 백엔드 변경 없음. tusd 핸들러, staging 디렉터리, finalize hook 모두 v0.3.0과 동일.
- 업로드 UI: panel, progress bar, drag-drop overlay — 변경 없음.
- 업로드 제한: `MAX_FILE_SIZE` env var, `MAX_CONCURRENT = 3` worker 캡 — 변경 없음.
- 영구 에러의 실패 시맨틱: 4xx는 여전히 즉시 `error`로 노출 (retry하면 실제 auth/validation 실패를 가림).

## 2. 검증 요약

**정적 검사**
- `npm run check`: 518 files, 0 errors, 2 warnings (둘 다 `Explorer.svelte` + `UserManager.svelte`의 `state_referenced_locally` — v0.3.0 기존 상태, 본 hotfix 범위 밖; v0.4.0 refactor branch에서 해소).
- `vite build`: production 번들 clean.

**Code review** — 양 변경 파일에 `/code-review` 14-criteria 통과:
- `tus-client.ts` (210 lines, post-fix): 14/14 ✅. 1차 pass에서 네이밍 `abortableSleep` (14자)과 `isTransientTusError` (19자)가 12자 규칙 위반 → `delay`와 `isTransient`로 자동 rename.
- `upload-worker.ts` (123 lines, post-fix): 14/14 ✅. 1차 pass에서 `runUpload`가 20-line SRP 캡 초과 → `buildTusOptions` + `handleUploadFailure` 헬퍼로 자동 분리.
- 0 ❌ Critical, 3 ⚠️ Warning 인라인 자동 수정, 0 deferred.

**End-to-end 업로드 smoke** — production NAS에서 사용자 검증 대기. hotfix는 behavior-additive (재시도가 없던 곳에 추가, 가짜 resume이 있던 곳을 진짜로 교체)이며 happy path (실패 0회 업로드)를 regress시킬 수 없다 — 새 코드 경로는 원래 코드가 실패했을 때만 실행. 배포 후 첫 대용량 파일 업로드에서 검증 권장: 전송 중 의도적으로 Wi-Fi blip 발생 → 업로드가 self-heal하는지 확인.
