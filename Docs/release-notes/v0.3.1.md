v0.3.1 is a **hotfix** for production large-file uploads. Every chunk PATCH the tus client made on v0.3.0 had zero retry on transient network failure — one Wi-Fi blip, brief proxy hiccup, or container restart anywhere in a multi-GB transfer caused `ERR_CONNECTION_RESET` and the entire upload aborted. The store's "Resume" action ALSO didn't really resume: it reset `uploadedBytes` to `0` and called the fresh-upload path, so re-trying a 50 GB upload restarted from offset 0. A real tus resume function existed in the client but was never wired to the worker.

---

## 1. Fix — TUS chunk retry + real resume

(commit `3c19a35`)

### What broke in v0.3.0

`frontend/src/lib/tus-client.ts`:
- `uploadChunk()` had no retry. Any `fetch` reject (transient network) or `5xx` response (server hiccup) threw immediately and surfaced as `ERR_CONNECTION_RESET` to the user.
- `resumeUpload(uploadUrl, ...)` (the real HEAD-then-PATCH-from-offset implementation) existed but had no caller.

`frontend/src/lib/upload-worker.ts`:
- `runUpload()` catch → immediate `setStatus("error")`. No transient-vs-permanent distinction.
- `resumeUpload(id)` (the worker's "Resume" handler) did `uploads.update(id, { status: "queued", uploadedBytes: 0 })`. The `uploadedBytes: 0` reset and the absence of the saved tus URL meant the next pump cycle re-created a fresh upload from scratch.

For a 50 GB transfer on a residential connection: one Wi-Fi blip → entire upload restarts from 0. The user-visible failure mode was `ERR_CONNECTION_RESET` in DevTools console + the upload marked `error` in the panel.

### What v0.3.1 changes

**`tus-client.ts` — retry + abort-aware backoff:**

- New `RETRY_DELAYS_MS = [500, 1000, 2000, 4000, 8000]` (cumulative ~15.5 s retry window).
- New `isTransient(error)` predicate: `TypeError` (fetch network reject) and `TusError` with `status === 0` or `status >= 500` are transient; `4xx` and `AbortError` propagate immediately.
- New `delay(ms, signal)`: resolves after `ms`, rejects immediately if the upload's `AbortSignal` fires. Pause/cancel during retry backoff is responsive.
- New `withRetry<T>(operation, signal)`: wraps `operation` in a `for` loop that catches transient errors and sleeps the next delay before re-trying. After `RETRY_DELAYS_MS.length` failed attempts, the original error propagates.
- `uploadChunk()` body wrapped in `withRetry` — chunks now survive blips, brief proxy timeouts, and short container restarts (watchtower rolling restart typically <10 s).
- `getOffset()` now takes `AbortSignal` (propagated from worker) and is also wrapped in `withRetry` — HEAD recovery during a resume is equally protected.
- `uploadFile()` exposes new `onCreate(uploadUrl)` callback. The worker uses it to persist the tus Location URL the instant CREATE returns — REQUIRED for genuine resume.

**`upload-worker.ts` — save tusUrl + real resume + transient→paused:**

- `buildTusOptions(upload)` extracted; wires `onCreate` to `uploads.update(upload.id, { tusUrl: uploadUrl })`.
- `runUpload()` now branches: if `upload.tusUrl && upload.uploadedBytes > 0`, calls `resumeTusUpload(upload.tusUrl, ...)` (the real `tus-client.resumeUpload` — HEAD for offset, PATCH from there). Otherwise, fresh `uploadFile(...)`.
- `handleUploadFailure(upload, error)` extracted; routes failures into three categories:
  - `AbortError` → silent (user-initiated cancel/pause)
  - `isTransient(error)` → `setStatus("paused", { errorMessage })`. `tusUrl` and `uploadedBytes` preserved on the upload row, so a user "Resume" continues from the last server-confirmed offset.
  - Anything else (4xx auth/validation/etc.) → `setStatus("error")` — same as before for permanent failures.
- `resumeUpload(id)` (the worker's public Resume handler) now preserves `uploadedBytes` when `tusUrl` exists. Reset-to-0 remains as a fallback only for legacy state where no `tusUrl` was ever saved.

### Behavior changes the user sees

| Scenario | v0.3.0 | v0.3.1 |
|---|---|---|
| Single chunk PATCH transient fail (Wi-Fi blip, brief 502) | Entire upload → `error` status, `ERR_CONNECTION_RESET` in console | Retry in 500 ms, 1 s, 2 s, 4 s, 8 s. If it succeeds anywhere in those 15.5 s, the upload continues seamlessly. |
| Chunk fails after retry exhausted (sustained outage) | Upload → `error`, must restart from offset 0 | Upload → `paused` with `tusUrl` + `uploadedBytes` preserved. Clicking "Resume" continues from the last server-confirmed offset (real tus HEAD→PATCH). |
| Server restart mid-upload (watchtower rolling restart, <10 s typical) | `ERR_CONNECTION_RESET`, upload lost | Retries absorb the restart window. Upload continues. |
| User clicks Pause then Resume on a partial upload | Resume restarted from 0 | Resume continues from the last confirmed offset. |
| Permanent 4xx (auth expired, forbidden, bad metadata) | `error` status | `error` status (unchanged — these are not retryable). |

### What did NOT change

- Server side: no backend changes. tusd handler, staging dir, finalize hook all identical to v0.3.0.
- Upload UI: panel, progress bar, drag-drop overlay — unchanged.
- Upload limits: `MAX_FILE_SIZE` env var, `MAX_CONCURRENT = 3` worker cap — unchanged.
- Failure semantics for permanent errors: 4xx still surfaces as `error` immediately (no retry — that would mask real auth/validation failures).

## 2. Verification Summary

**Static checks**
- `npm run check`: 518 files, 0 errors, 2 warnings (both `state_referenced_locally` on `Explorer.svelte` + `UserManager.svelte` — pre-existing v0.3.0 state, out of scope for this hotfix; addressed in the v0.4.0 refactor branch).
- `vite build`: production bundle clean.

**Code review** — `/code-review` 14-criteria pass on both changed files:
- `tus-client.ts` (210 lines, post-fix): 14/14 ✅. Naming `abortableSleep` (14 chars) and `isTransientTusError` (19 chars) failed the 12-char rule on first pass → auto-renamed to `delay` and `isTransient`.
- `upload-worker.ts` (123 lines, post-fix): 14/14 ✅. `runUpload` exceeded 20-line SRP cap on first pass → auto-split into `buildTusOptions` + `handleUploadFailure` helpers.
- 0 ❌ Critical, 3 ⚠️ Warning auto-fixed inline, 0 deferred.

**End-to-end upload smoke** — DEFERRED to user verification on the production NAS. The hotfix is behavior-additive (retry where there was none, real resume where there was a fake one) and cannot regress the happy path (zero-failure upload) — the new code paths only execute when the original code would have failed. Verification recommended on the first large file upload after deployment: trigger a deliberate Wi-Fi blip mid-transfer and confirm the upload self-heals.
