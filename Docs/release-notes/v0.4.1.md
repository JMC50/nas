v0.4.1 is a **security fix. Upgrade now if Google sign-in is enabled.**

---

## 1. Fix: Google sign-up trusted the user ID in the request

`POST /auth/google/register` (also under `/server/...`) took `userId` from the request body without asking Google who the caller was. It saved that user and returned a token for it. When `userId` matched an existing account, the handler updated that account and issued a token for it. Anyone who knew another user's Google account ID could sign in as that user, including an admin.

Discord sign-up was not affected: it already looks the user up at Discord with the caller's access token.

**What changed:**

- `GET /auth/google/callback` now also returns the Google `access_token` when it answers `"status": "new"`.
- `POST /auth/google/register` takes `{ "access_token", "krname" }`. It fetches the user from Google with that token and uses Google's ID, name and email. Any `userId`, `username`, `email` or `global_name` in the body is ignored.
- An invalid or missing token gets `502 google lookup failed` and no account or token.
- The Google sign-up screen sends the access token instead of the user fields.

**If you cannot upgrade at once,** block `POST /auth/google/register` and `POST /server/auth/google/register` at your reverse proxy. Existing Google users can still sign in, because sign-in uses `/auth/google/callback`.

**Check your users** for accounts or changed names you do not recognize. The handler overwrote `username`, `global_name` and `krname` of the account it was given.

---

## 2. Upgrade notes

- No schema change.
- Clients that call `/auth/google/register` directly must send `access_token` from the callback response.
