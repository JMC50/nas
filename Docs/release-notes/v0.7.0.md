v0.7.0 adds **single sign-on with OpenID Connect**: with `AUTH_TYPE=oidc`, one issuer is the only way to sign in. Deployments that keep `local`, `oauth`, or `both` work as before and need no new setting.

## 1. Single sign-on mode (`AUTH_TYPE=oidc`)

(commits `ea98df0`, `e72f5e8`, `74e7a98`, `02d8212`, `3d49e4e`, `c5ec7c3`, `ea067a3`)

**What it does.** The sign-in page has no ID or password form and no Discord or Google button. It sends the browser to the issuer. After sign-in at the issuer, the person is signed in to the NAS.

**Flow.** Authorization code with PKCE (`S256`), `state`, and `nonce`. The NAS reads the endpoints and keys from the discovery document and verifies the signature, issuer, audience, expiry, and nonce of the ID token. The redirect address comes only from `OIDC_REDIRECT_URI`. The state cookie and the hand-over cookie are `Secure`, `HttpOnly`, `SameSite=Lax`, and short-lived (10 minutes and 60 seconds). The name of the state cookie ends with the state, so each sign-in has its own cookie. Sign-ins in two tabs at the same time both succeed. When 5 unfinished sign-ins have accumulated, the next sign-in removes their cookies. The NAS token is never part of an address.

**Settings:**

| Variable | Required | Default |
|---|---|---|
| `OIDC_ISSUER`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`, `OIDC_REDIRECT_URI` | Yes, with `AUTH_TYPE=oidc` | |
| `OIDC_IDP_HINT` | No | |
| `OIDC_SCOPES` | No | `openid profile email groups` |
| `OIDC_GROUPS_CLAIM` | No | `groups` |
| `OIDC_MEMBER_GROUP`, `OIDC_ADMIN_GROUP` | No | `nas_member`, `nas_admin` |
| `OIDC_LOGOUT_URL` | No | `end_session_endpoint` of the issuer |

With `AUTH_TYPE=oidc` and a missing required value, the server does not start and names the missing variables. `OIDC_ISSUER` must use `https`. Plain `http` is accepted only for `localhost` and loopback addresses such as `127.0.0.1`.

**Check of the `AUTH_TYPE` value.** `docker run --env-file` keeps quotes, trailing spaces, and a `# comment` after the value. So the server does not start in these two cases:

- The value becomes `oidc` only after spaces, quotes, and a comment are removed and the letters are changed to lower case. Examples: `OIDC`, `oidc   # comment`.
- `AUTH_TYPE` is not `local`, `oauth`, `both`, or `oidc`, and one of `OIDC_ISSUER`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`, `OIDC_REDIRECT_URI` is set.

Any other unknown value starts the server as in v0.6.0, and the log shows the warning `AUTH_TYPE is not one of local, oauth, both, oidc`.

**Users and groups:**

- The NAS finds the user by the `sub` claim (identity `oidc`). If there is none, it creates the user.
- The member group gives a new user `VIEW`, `OPEN`, `DOWNLOAD`, `UPLOAD`, `COPY`, and `RENAME`. The admin group gives `ADMIN`.
- A person in none of the two groups is refused, and no user is created.
- Groups set the permissions only when the user is created. Later changes are made in the user manager.

**Closed routes.** In this mode the server answers `403` on local sign-in and registration, change-password, the Discord and Google callbacks and registrations, the link routes, identity removal, and `POST /requestAdminIntent`, which gives `ADMIN` for the admin password. A password gives no permission in this mode. `ADMIN` comes only from the admin group or from an administrator in the user manager. The front end does not show the buttons that ask for the admin password in this mode. `GET /auth/config` reports only OIDC.

**Sign-out.** The front end removes the NAS token and opens the end-session address of the issuer.

Setup guide: [Single Sign-On with OpenID Connect](https://github.com/JMC50/nas/blob/main/Docs/configuration/oidc-sso.md).

## 2. Back-channel logout and token validity

(commits `5307d52`, `e72f5e8`, `40686bb`, `be896ab`, `8a07c96`)

**Back-channel logout.** The issuer can call `POST /auth/oidc/backchannel` with a `logout_token`. The NAS verifies the signature, `iss`, `aud`, `exp`, `iat`, the logout event, and that there is no `nonce`. It refuses a token that was used before. The request body can be up to 8 KiB. A `logout_token` signed with a 4096-bit RSA key is about 1.3 KiB.

**Status codes.** A token that is not valid gets `400`. When the NAS cannot read the discovery document or the keys of the issuer, it cannot check the token and answers `503`. The issuer can send the same token again.

**Token validity.** Each user has a new value `tokens_valid_after`. It is empty by default, which means no restriction. A back-channel logout sets it to the current time. The token check then rejects each token of that user that was issued earlier, with `401`. New tokens carry the claim `issued_at` for this comparison.

In `oidc` mode the token check also rejects the token of a user who was deleted from the NAS. When the NAS creates a user at the first sign-in, it sets `tokens_valid_after` to the time of creation. So if a deleted user signs in again and gets a new user with the same `userId`, the tokens of the deleted user stay rejected. The token that the NAS issues right after it creates the user is accepted, also in the same millisecond.

## 3. `oidc-link` command for existing deployments

(commits `7d4bace`, `d413279`)

A deployment that moves from `oauth` or `local` to `oidc` keeps its users with this command. It reads a CSV file with the old ID and the new `sub` of each person, and adds the `oidc` identity to the existing user. The user ID, permissions, and files stay the same.

```bash
docker exec nas-app /app/server oidc-link --map /tmp/oidc-map.csv --from google --dry-run
```

- `--dry-run` reports each line and writes nothing.
- The command can run again with the same file.
- A UTF-8 BOM at the start of the file (Excel writes one) and spaces around each value are ignored.
- The output shows NAS user names and line numbers. It shows no ID, no `sub`, and no secret.

## 4. Upgrade notes

- **Other modes are unchanged.** With `AUTH_TYPE` not set, `local`, `oauth`, or `both`, no new setting is needed and the `OIDC_*` variables are not read. The admin password route works as before. The response of `GET /auth/config` has the same fields as in v0.6.0.
- **The `/auth/oidc/` addresses in other modes.** No route exists for them, so they are handled like any unknown address. When `FRONTEND_DIR` is set, as in the Docker image, the answer is `200` with the `index.html` of the front end, also for `POST`. Without `FRONTEND_DIR` the answer is `404`. In both cases no cookie is set and nothing changes in the NAS. A deployment that goes back from `oidc` to another mode should remove the back-channel logout URI at the issuer.
- **`AUTH_TYPE` value.** A value in one of the two cases above now stops the start. Any other unknown value starts as before and only writes a warning.
- **Database.** The server adds the column `users.tokens_valid_after` at startup. The change is automatic and keeps all rows. v0.6.0 also starts with the changed database.
- **Tokens.** A token from v0.6.0 stays valid. Nobody is signed out by the upgrade.
- **Token check.** Each request with a token now reads `tokens_valid_after` of the user. `POST /log`, the start of a resumable upload, and change-password use the same check.
- **Front end in other modes.** The sign-in page shows its subtitle after the configuration is loaded. Sign-out reads `/auth/config` before it leaves the page.
- **Reverse proxy.** A deployment that uses `oidc` must pass `/auth/oidc/` like the other API routes, and the NAS must be served over HTTPS.
- **New dependencies.** `github.com/coreos/go-oidc/v3` v3.21.0 and `golang.org/x/oauth2` v0.36.0, and `github.com/go-jose/go-jose/v4` v4.1.9 through them. go-jose v4.1.4 has public advisories (GHSA-mgcc-cww5-fp2q, GHSA-4w3g-jfj2-cw2q, GHSA-vvm8-gf78-28g4), so the NAS uses the fixed v4.1.9. The unauthenticated `/auth/oidc/backchannel` route reads tokens with this library.

## 5. Known limits

- The list of used `logout_token` IDs is in memory. After a restart, a `logout_token` younger than 5 minutes is accepted one more time.
- A `logout_token` with only `sid` and no `sub` is refused.
- An unknown signing key in a `logout_token` makes the NAS read the keys of the issuer again. Limit the request rate of `/auth/oidc/backchannel` at the reverse proxy when the address is public.
- Since go-jose v4.1.6, RSA keys larger than 4096 bits are refused. If the signing key of the issuer is larger, sign-in and back-channel logout do not work.
- Public download links of a user stay valid after a back-channel logout.
- In production (`NODE_ENV=production`), the server needs `ADMIN_PASSWORD` to start, also in `oidc` mode. This mode does not use the value.
- When `NODE_ENV` is not `production`, the server starts without `PRIVATE_KEY` and accepts tokens signed with the empty key. This is the same since v0.6.0. The Docker image and `docker-compose.yml` set `NODE_ENV=production`. Keep this value in a real deployment.
- The Discord and Google sign-in code stays in the server and is closed only by the mode.
